# 18.2 流水线处理器

> **前置知识**：[18.1 从逻辑门到单周期处理器](18.1-从逻辑门到单周期处理器.md)（单周期数据通路）。本节将其切段流水化，并处理流水线带来的冒险问题——这是进入19章超标量微架构的最后一级台阶。

---

## 1. 流水线：切分与重叠

### 1.1 切成五段

沿用18.1的延迟数据，把单周期切成5段，每段之间插入流水线寄存器：

```
IF     ID     EX     MEM    WB
取指   译码   执行    访存   写回
2      1      2       4      1        ← 各段延迟
```

```
时钟周期 →   1    2    3    4    5    6    7    8    9
指令1:      [IF] [ID] [EX] [MEM][WB]
指令2:           [IF] [ID] [EX] [MEM][WB]
指令3:                [IF] [ID] [EX] [MEM][WB]
指令4:                     [IF] [ID] [EX] [MEM][WB]
                                ↑ 充满后每周期完成一条指令
```

### 1.2 性能计算

- 时钟周期 = 最慢段的延迟 = 4（访存段），不再是10
- 吞吐量：稳态下**每周期完成一条指令**（IPC = 1）
- 加速比（理想）= 段数（受最慢段限制，实际达不到）

**代价**：每段之间的流水线寄存器增加面积和（setup时间带来的）延迟；指令总延迟反而略微增加。

**实现视角**：这里"在组合逻辑各段之间插入时钟触发的寄存器"正是 RTL 流水线设计要做的递推与切级工作，如何在 Verilog/SystemVerilog 里实现并用寄存器把长组合路径打散，参见第 6.5 章 §11 流水线设计（[6.5 RTL 设计](../芯片设计/6.5-RTL设计.md)）。

### 1.3 流水线寄存器

段间寄存器锁存该段的所有结果和下游需要的控制信号：

```
IF/ID寄存器:  指令字、PC+4
ID/EX寄存器:  读出的寄存器数据、立即数、控制信号
EX/MEM寄存器: ALU结果、写数据、访存控制
MEM/WB寄存器: 加载的数据、写回目标
```

## 2. 冒险：流水线的三种故障

### 2.1 结构冒险（Structural Hazard）

**同一硬件被两段同时需要**。经典案例：单端口存储器同时被IF（取指令）和MEM（访数据）使用。

```
周期4: 指令3的IF 和 指令1的MEM 争同一个存储器 → 冲突
```

**解决**：哈佛结构——指令存储器与数据存储器分离（现代CPU的L1 I-cache/D-cache分离即源于此）。

### 2.2 数据冒险（Data Hazard）

**后一条指令需要前一条还没写回的结果**：

```
add x1, x2, x3    ; x1 在周期5(WB)才写回
sub x4, x1, x5    ; 周期3(ID)就要读 x1 → 读到旧值！
```

#### 解法一：转发（Forwarding/Bypass）

ALU结果其实周期3(EX结束)就有了，不必等WB。加一条旁路路径直接送到下一条指令的ALU输入：

```
EX/MEM寄存器的ALU结果 ──(转发多选器)──→ 下一条指令的ALU输入
MEM/WB寄存器的结果    ──(转发多选器)──→ 更后面指令的ALU输入
```

**转发判定逻辑**：

```
if (EX/MEM.RegWrite && EX/MEM.rd != 0 && EX/MEM.rd == ID.rs1)
    ALU输入1 ← 转发EX/MEM的结果
```

#### 解法二：加载-使用冒险必须停顿一拍

```
lw  x1, 0(x2)     ; 数据周期4(MEM末)才有
add x3, x1, x4    ; 周期4(EX)就要用 → 转发也来不及！
```

**解决**：硬件插入一个"气泡"（stall），配合转发：

```
lw  x1, 0(x2)     [IF][ID][EX][MEM][WB]
气泡(bubble)                    [--][--]        ← 冻结PC和IF/ID寄存器
add x3, x1, x4         [IF][ID][stall][EX][MEM][WB]
                                        ↑ MEM/WB→EX转发
```

编译器调度（重排指令填空泡）可消除大部分此类停顿。

### 2.3 控制冒险（Control Hazard）

**分支指令到EX/MEM才知道方向，取指早已走远**：

```
beq x1, x2, target   [IF][ID][EX]  ← 周期3才知是否跳转
下一条指令?           [IF][ID]     ← 周期1就得决定从哪取！
```

**解法梯队**（19.1节分支预测的完整展开正是从这里出发）：

| 层级 | 方法 | 代价 |
|------|------|------|
| 最保守 | 停顿到分支结果出来 | 每次3周期气泡 |
| 简单 | 静态预测（向后跳/向前不跳） | 循环友好 |
| 实用 | 2位饱和计数器 + BHT | 90~95%准确 |
| 现代CPU | TAGE/ITTAGE/多级BTB | 99%+（见19.1） |
| 编译器 | 延迟槽（早期MIPS）/ 调度 | 部分隐藏 |

**误预测代价** = 分支解析周期数 ≈ 流水线前端深度。这解释了为什么深流水线（19章的17~19级）必须配极准的预测器。

## 3. 分支提前与高级优化（通往超标量）

### 3.1 把分支判定移到ID段

在ID段加一套专用比较器，分支在周期2就解析——误预测代价从3降到1。代价：ID段变复杂、又产生新的数据冒险（分支比较依赖前序ALU结果时需要专用转发）。

### 3.2 更宽的发射：超标量

五级流水线IPC上限=1。突破方法：

- **多发射**：每周期取指/译码/发射N条 → 19.1的超标量
- **乱序执行**：让不相关的指令越过停顿的指令 → 19.1的Tomasulo
- **推测执行**：预测分支后提前执行 → 19.1的推测与恢复

### 3.3 更深的流水线：超流水

把每段再切细提高主频——但每段流水线寄存器开销占比上升，且误预测代价增大。Pentium 4的31级深流水线（见19.1表）就是走极端的教训。

## 4. 异常与中断

前面处理三种冒险，都假设程序"顺利执行"。但CPU必须同时响应两类"不顺"——异常与中断。两者都会打断指令流，但来源与时机完全不同。

### 4.1 异常（同步）与中断（异步）

| 特性 | 异常（Exception） | 中断（Interrupt） |
|------|------------------|-------------------|
| 来源 | 指令自身触发（**同步**） | 外部事件触发（**异步**） |
| 例子 | 未定义指令、除零、地址越界/对齐错误、页错误、syscall | 外设请求、定时器到期、DMA完成、外部信号 |
| 时机 | 由正在执行的指令决定，可预期 | 与当前指令无关，随时可能到 |
| 可重试 | 非法指令/除零不可重试；页错误可重试 | 处理完返回后继续原程序 |

> **术语提醒**：x86 习惯把两类都叫"中断"（其IDT里区分 fault/trap）；RISC-V 与 ARM 则严谨区分 exception（异常）与 interrupt（中断）。本节按 RISC-V 习惯，"异常"专指同步事件。

### 4.2 为什么精确异常（precise exception）很难

多级流水线里，多个阶段的指令同时在流水中。若第 $k$ 条指令在EX段出错（如除零），而第 $k+2$ 条已经在MEM/WB段写回——处理器状态已经"越过"出错指令前进了一步：

```
lw   x1, 0(x2)     周期5已WB    ← 结果已写回寄存器
div  x3, x4, x0    周期4在EX段除零 → 出错
add  x5, x6, x7    周期3还在ID段
```

如果div出错时lw的结果已经生效，处理器就落入"异常指令之后的指令已写回"的混乱状态，无法准确恢复。

**精确异常（precise exception）** 的定义：

- 异常在**一条指令边界**上报告——该指令要么完全执行，要么完全不执行；
- 异常指令**之后的指令一律不得写回**寄存器或内存；
- 此时处理器架构状态与"按程序顺序执行到该指令"完全一致。

精确异常的价值：程序可以被安全地打断、处理、再从异常返回精确继续执行（调试器单步、页错误重取页、模拟器、性能事件采样都依赖它）。

### 4.3 简单的处理流程

在经典五级流水线里，检测到异常后按顺序执行：

```
① 暂停（stall）整个流水线：冻结PC和各级流水线寄存器
② 作废（flush）异常指令之后已进入流水的所有指令，
   把"它们尚未写回"变成确定的事实
③ 把异常指令的地址存入 EPC/返回寄存器
   （RISC-V 的 mepc，x86 通过栈压入返回地址），供处理后返回
④ 跳转异常处理例程（异常向量）：PC ← 向量基址 + 编号×偏移
⑤ 处理完成后从 EPC 恢复，重新执行那一条指令（或直接返回）
```

```
检测到异常
   ↓
暂停流水线  →  flush后续指令  →  保存 EPC  →  跳转异常向量
                                            ↓
              处理例程：读异常原因/编号 → 处理 → 返回原指令
```

### 4.4 与流水线其他机制的配合

- **异常 vs 分支误预测**：分支误预测是"预测猜错了方向"，异常是"指令本身非法或特殊事件"——异常的 flush 语义更重，必须保证不留下任何越界副作用。
- **异步中断**可在任意周期到达：在指令边界处采样，视作"下一条指令之前"的异常处理，天然满足精确异常。
- **在乱序处理器中**，"暂停+flush"无法这样朴素地做——多指令并行乱序执行，异常不能再从某一条指令就地触发。这需要 ROB 在提交点统一报告异常（见19.1 §5.4）。

## 5. 带转发与冒险检测单元的完整流水线数据通路

前面把转发、气泡、flush 的解法一个个摆了开来。现在把它们装配成一张完整的五级流水线数据通路图，并由两个专用单元——**转发单元（Forwarding Unit）** 与 **冒险检测单元（Hazard Detection Unit）**——来"自动驾驶"这条流水线。

### 5.1 数据怎么在五段间流动

沿 1.3 的段间寄存器，各段把结果锁存后交给下游：

| 段间寄存器 | 装入的内容 | 由谁向下游消费 |
|-----------|-----------|--------------|
| IF/ID | 指令字、PC+4 | ID 用于译码、读寄存器堆 |
| ID/EX | 读出的 rs1/rs2 数据、立即数、目标 rd、控制信号 | EX 作为 ALU 输入与选择 |
| EX/MEM | ALU 结果、写数据、访存控制信号、目标 rd | MEM 访存；同时可作转发源 |
| MEM/WB | 存储器读出的数据或 ALU 结果、目标 rd | WB 写回寄存器堆；可作转发源 |

主数据流是**单向向后**的：指令从 IF 推进到 WB。但 EX/MEM 与 MEM/WB 里的结果还必须"回头"送到更靠前的 EX 段（5.2），这条路是专为数据冒险加的旁路。

### 5.2 转发单元（Forwarding Unit）

EX 段的 ALU 有两个输入，每个都接一个 **旁路多选器**：

- 默认输入：ID/EX 寄存器里译码阶段读出的寄存器数据（rs1 / rs2 的值）；
- 转发输入：既可来自 **EX/MEM** 寄存器的 ALU 结果（1 拍前的指令），也可来自 **MEM/WB** 寄存器（2 拍前的指令）。

```
转发源       1拍前(EX/MEM)  2拍前(MEM/WB)
               ▼                ▼
read_data1 ─▶ [旁路MUX] ─▶ ALU输入1
read_data2 ─▶ [旁路MUX] ─▶ ALU输入2
控制线 ↑──────────────┘        ▲ 由转发单元(ForwardingUnit)选通
```

转发单元根据 "被使用寄存器是否等于上游正在写回的 rd" 来决定选哪个源，规则为**就近优先**：

| 情形 | 判定条件（针对当前处于 EX 段的指令） | 结果 |
|------|------------------------------------|------|
| EX 冒险（1拍前指令供数） | `EX/MEM.RegWrite && rd≠0 && EX/MEM.rd==ID/EX.rs1(或rs2)` | 输入取自 EX/MEM.ALU结果 |
| MEM 冒险（2拍前指令供数） | `MEM/WB.RegWrite && rd≠0 && MEM/WB.rd==ID/EX.rs1(或rs2)` 且未命中上述 EX 冒险 | 输入取自 MEM/WB 结果 |
| 回写 x0 | 目标为 `x0` 不转发（x0 恒为0） | 走默认寄存器读值 |

**就近优先的原因**：当两个来源同时都能提供时，取更靠近当前指令的那个——EX/MEM 里的结果比 MEM/WB 里的更新。例如：

```
add x1, x2, x3   ; 本条在 EX：结果刚进 EX/MEM
sub x4, x1, x5   ; 本条在 EX：EX/MEM.rd=x1 == rs1 → 转发 EX/MEM→ALU
```

有了这一层，绝大多数 RAW 数据依赖无需停顿，只有"加载-使用"那种"转发也来不及"的情形才落到 5.3。

### 5.3 冒险检测单元（Hazard Detection Unit）

它的核心任务只有一个：**检测 load-use 数据冒险，并在必要时插入一拍气泡**（顺带配合分支 flush，见 5.4）。

判定发生在 ID 阶段（此刻 load 已经离开 ID/EX 寄存器、正在 EX 段执行）：

```
if (ID/EX.MemRead == 1                     // EX段指令是一条 load
    && ID/EX.rd != 0
    && (ID/EX.rd == IF/ID.rs1 || ID/EX.rd == IF/ID.rs2)) {
    // 下一条指令(在ID)要用 load 的目标值，转发已来不及 → 停一拍
    冻结PC；冻结IF/ID寄存器；把ID/EX控制信号清零(插气泡)
}
```

插入气泡时同时做三件事（与 2.2 一致）：

1. **冻结 PC**：本周期不更新，下周期仍取同一条指令；
2. **冻结 IF/ID 寄存器**：使译码阶段看到的仍是同一条"使用指令"，防止它被再次译码或丢失；
3. **清零 ID/EX 寄存器**：在 EX 段"塞入"一条无效指令，让它空转一个周期，避免把上一拍已译码的内容误推进流水线。

时间线示意：

```
周期       3       4       5       6       7      8
lw  x1,0(x2)  [EX]   [MEM]   [WB]
add x3,x1,x4  [ID]   [stall] [ID]   [EX]   [MEM]  [WB]
                     ↑气泡    ↑重新译码  ↑经MEM/WB→EX走转发
```

### 5.4 完整装配：五段 + 两个单元

```
主数据流（单向前进）：
IF ──▶ ID ──▶ EX ──▶ MEM ──▶ WB
└IF/ID┘  └ID/EX┘   └EX/MEM┘  └MEM/WB    ← 段间流水线寄存器

转发通路（把结果回头送回 EX 的 ALU 输入）：
EX/MEM.ALU结果 ───────────────────────▶ EX旁路MUX   1拍前的结果
MEM/WB.结果    ───────────────────────▶ EX旁路MUX   2拍前的结果

两个专用单元的职责分工：
冒险检测单元：load-use → 冻结PC + 冻结IF/ID + 清零ID/EX（插气泡）
             分支解析到 → 清零IF/ID 已取入的指令（flush）
转发单元：按就近优先选通上述两支旁路MUX

控制通路：控制信号在ID按opcode一次性生成后，随各级寄存器逐段下传（见第6节）。
```

## 6. 控制信号的逐段传递

单周期里（18.1），控制器在一个时钟内根据 opcode 一次性生成全部控制信号。流水线不能这样做——同一时刻有 4~5 条指令各处在不同段，若每段都重新译码，既浪费硬件，也容易错配。解决办法是：**控制信号在 ID 阶段一次确定，然后与对应指令的数据在同一条段间寄存器里逐级向后携带**。

关键点：控制与数据锁存于**同一条**流水线寄存器，因此第 $k$ 条指令的 `ALUop` 永远不会用到第 $k+1$ 条指令的数据上去——它们始终对齐前进。

| 控制信号 | 生成段 | 被使用段 | 作用 |
|---------|-------|---------|------|
| RegWrite | ID | WB | 决定是否写回寄存器堆 |
| MemWrite / MemRead | ID | MEM | 决定访存是写还是读 |
| MemtoReg | ID | WB | 写回数据来自存储器还是 ALU |
| ALUOp / ALUsel | ID | EX | 决定 ALU 做什么运算 |
| Branch / Jump | ID | EX（改良后也用于ID，见3.1） | 分支/跳转是否成立 |
| RegDst / rd 来源 | ID | WB | 写回哪个寄存器 |

逐段传递的机制可以概括为三步：

1. **只译码一次**：后续各段不再重新判断指令类型，只按需取用已携带的控制位；
2. **按段剥离**：每段只消费自己那一拍需要的位，其余位随寄存器继续向右传递；
3. **对齐保证**：控制与数据同进同退，任何一段都不会"借用"别的指令的配置。

气泡与 flush 也借此实现（呼应 5.3）：stall 时把 ID/EX 寄存器的控制位**整体清零**，形成一条"无效指令"，即使它流过 EX→MEM→WB，其 `RegWrite=0`、`MemWrite=0`，不会改写任何寄存器或内存——这正是"空窗"的本质。

## 7. 分支预测基本原理

2.3 的梯队表和 3.1 的分支前移已经交代了"为什么"与"往高级走"的方向，这里补上底层原理：静态预测、动态预测、2 位饱和计数器与 BHT。

### 7.1 预测的成本与意义

分支在 ID（改良后）或 EX 才解析，而取指在 IF 早就发生。每次误预测的代价 = 分支解析所需的周期数（≈前端深度）。对 CPI 的贡献可写成：

```
控制冒险CPI贡献 = 分支指令占比 × 误预测率 × 每次误预测代价
```

预测的目标就是压低"误预测率 × 代价"两项（第8节有数字示例）。

### 7.2 静态预测（Static Prediction）

不依赖运行历史，取指时按固定规则猜测：

- **预测不跳转（not taken）**：顺序取指即可，成本为零。但分支相当比例确实会跳，命中率往往不足 50%~70%。
- **预测跳转（taken）**：对"总是跳"的分支（如循环体的无条件跳）效果好。
- **BTFNT（backward taken, forward not taken）**：按分支方向启发——向后跳（面向循环）猜"跳"、向前猜"不跳"。代码以循环为主时准确率不错。
- **编译期/Profile 引导**：编译时统计分支实际方向，把"大概会跳"的标记固化进指令，是静态预测的加强版。

静态预测硬件简单、功耗低，但准确率上限不高，属于"简单"档（对照 2.3 梯队表）。

### 7.3 动态预测（Dynamic Prediction）

运行时根据每条分支的**历史**实时更新预测：

- **1 位预测器**：记录上次实际方向，作为本次预测。缺陷是"两连错"——循环退出那一次猜反后，需再出现一次同类结果才能稳定，导致在循环边界反复犹豫。
- **2 位饱和计数器**：对单次"意外"（如循环末尾那一次）不敏感，是经典的性价比之选，见 7.4——这也是 2.3 表中"实用"档（90~95%）的来源。

### 7.4 2 位饱和计数器与 BHT

每个分支一个 2 位状态机（4 态），状态在两个方向上分别各存"强/弱"两级：

```
实际taken：  状态值+1，封顶为"强跳"(11)
实际未跳：  状态值−1，封底为"强不跳"(00)

      强不跳(00) → 弱不跳(01) → 弱跳(10) → 强跳(11)
         (预测不跳)            (预测跳)
实际taken      ──(+1)────▶────▶────▶
实际未跳      ◀──(−1)────◀────◀────
判跳规则：处于"弱跳/强跳"时预测跳转，否则预测不跳
```

**性质**：需要连续两次实测与当前预测相反，才真正翻转方向——恰好容忍单次抖动（循环末尾那次退出）。相比 1 位预测器循环边界准确率明显更高，这是它成为经典方案的核心理由。

**BHT（Branch History Table，分支历史表/预测缓冲区）**：一张以计数器数组为核心的小查找表，用分支地址的低位（PC 的部分位）做索引，每个表项存一个 2 位饱和计数器。分支解析后按实际方向更新对应表项，下一条**同地址**分支取指时据此预言方向。

- **别名/冲突**：PC 低位相同的不同分支会共享表项、互相覆盖，略降准确率；可用更大的表或更均匀的 hash 缓解。
- **BHT vs BTB**：BHT 只回答"跳/不跳（方向）"；**BTB（Branch Target Buffer）** 额外缓存跳转目标地址甚至目标指令，免去向目标取指的那一拍。深流水线往往两者并存——这正是 19.1 多级预测器的入口。

## 8. CPI 定量分析

把前面的定性讨论落到数字上，用一个公式和一条代码剖面算出流水线的 CPI。

### 8.1 公式

```
CPI流水线 = CPI理想 + CPI数据冒险 + CPI控制冒险 + CPI结构冒险
CPI理想   = 1                     （稳态每周期完成一条，IPC=1）
CPI数据冒险 = (load-use 次数 × 1) / 指令数     （转发已消除大多数RAW）
CPI控制冒险 = (分支数 × 误预测率 × 误预测代价) / 指令数
CPI结构冒险 = 资源冲突停顿 / 指令数            （分离I/D cache下通常为0）
```

这里假设哈佛结构消除了结构冒险，聚焦剖析前两类。

### 8.2 一个带数字的示例

设一段程序共 $N=1000$ 条指令，混合为：25% 分支、20% load、其余 ALU/store 等。再设定：

- 转发齐全 → 除 load-use 外无数据停顿；
- 一半 load 的后一条指令立刻使用该值 → load-use 次数 $=200\times\frac12=100$ 次，每次 1 拍 → **数据冒险停顿 100 周期**；
- 分支在 ID 段解析（采用 3.1 改良，代价 1 拍），2 位饱和计数器 + BHT 预测准确率 90%（误预测率 10%）→ 误预测次数 $=250\times10\%=25$，各 1 拍 → **控制冒险停顿 25 周期**。

逐项累加：

| 项 | 周期数 | 对 CPI 贡献 |
|----|-------|------------|
| 理想执行 | 1000 | 1.000 |
| load-use 数据停顿 | 100 | 0.100 |
| 分支误预测停顿 | 25 | 0.025 |
| **合计** | **1125** | **1.125** |

即 $CPI = (1000+100+25)/1000 = 1.125$，IPC $=1/1.125\approx0.89$。

对照一下：若分支仍在 EX 段解析（代价 2 拍），控制停顿变 $25\times2=50$，CPI 升到 $1.15$；代价 3 拍则是 $1.175$——这正是 3.1 "把分支判定移到 ID 段"的价值所在。

### 8.3 与单周期对照

- 单周期：每条指令 10 周期 → $1000\times10=10000$ 周期；
- 流水线：$1125$ 周期；
- 实测加速比 ≈ $10000/1125\approx8.9$，已逼近理想上限 10（受最慢段与段间寄存器开销限制，达不到）。

从这个例子还能看出：**真正难啃的是最慢段与预测准确率**。把预测精度提到 98%，控制停顿降到 5 周期，CPI≈1.105，加速比≈9.05——增益有限；反之，若分支占比变高或误预测代价变大，收益会迅速被磨平。这正是 19 章深流水线要把大量面积和延迟砸在"更准的预测器"上的原因。

## 9. 五级流水线 vs 现代CPU

| 特性 | 经典五级 | 现代超标量（19章） |
|------|---------|------------------|
| 发射宽度 | 1 | 6~10 |
| 执行顺序 | 按序 | 乱序（ROB提交） |
| 分支处理 | 停顿/静态预测 | 多级预测器+推测执行 |
| 数据冒险 | 转发+停顿 | 寄存器重命名消除伪依赖 |
| 加载延迟 | 1段 | L1命中4~5周期，乱序隐藏 |
| IPC | ≤1 | 4~6 |

**五级流水线是骨架，超标量是在骨架上长出的器官**——19.1将逐个展开这些器官。
