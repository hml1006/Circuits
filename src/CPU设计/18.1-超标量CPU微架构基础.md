# 18.1 超标量CPU微架构基础

## 1. ISA与微架构

### 1.1 指令集架构（ISA）

指令集架构是计算机软件与硬件之间的接口契约。ISA定义了处理器能够执行的指令、寄存器、内存模型和异常处理机制。

**两大主流ISA阵营**：

| 特性 | x86_64 (Intel/AMD) | AArch64 (ARM) |
|------|-------------------|--------------|
| 指令长度 | 变长（1\~15字节） | 定长（4字节） |
| 寄存器数量 | 16个通用寄存器（GPR） | 31个通用寄存器（X0\~X30） |
| 架构风格 | CISC（复杂指令集） | RISC（精简指令集） |
| 指令编码 | 复杂，多格式 | 统一，规整 |
| 条件码 | EFLAGS标志位 | 条件执行指令 |
| 内存寻址 | 多种复杂寻址模式 | 基址+偏移量 |

### 1.2 微架构（Microarchitecture）

微架构是ISA的**具体硬件实现**。同一ISA可以有完全不同的微架构实现：

- x86_64: Intel Core (Sunny Cove/Golden Cove/Lion Cove) vs AMD Zen (Zen 1\~5)
- AArch64: ARM Cortex-X系列 vs Apple Silicon (Firestorm/Icestorm) vs Qualcomm Oryon

**现代超标量CPU的核心特征**：

> 超标量（Superscalar）：每个时钟周期发射多条指令
> 乱序执行（Out-of-Order）：指令不按程序顺序执行
> 推测执行（Speculative Execution）：提前执行可能需要的指令

## 2. 流水线基础

### 2.1 经典五级流水线

最简单的RISC流水线分为5级：

```
IF → ID → EX → MEM → WB
取指  译码  执行  访存  写回
```

**每级功能**：
- **IF（取指）**：从指令缓存中读取指令，更新PC
- **ID（译码）**：解码指令，读取寄存器，生成控制信号
- **EX（执行）**：ALU运算，地址计算，分支判断
- **MEM（访存）**：数据缓存访问（加载/存储）
- **WB（写回）**：将结果写回寄存器文件

**理想吞吐量**：每个时钟周期完成一条指令。

### 2.2 流水线冒险

#### 数据冒险（Data Hazard）

当指令之间存在数据依赖时发生：

```
ADD  X0, X1, X2   ; 写入 X0
SUB  X3, X0, X4   ; 读取 X0 → RAW 冒险
```

**解决方法**：
1. **转发（Forwarding/Bypassing）**：将EX级的结果直接转发给下一指令的EX级输入，无需等待WB
2. **插入气泡（Stall）**：当无法转发时（如加载指令后紧跟使用），插入NOP等待

**加载使用延迟（Load-use Latency）**：加载指令后紧跟使用加载结果的指令，即使转发也需要1个气泡：

```
LDR  X0, [X1]     ; 加载，MEM级才得到结果
ADD  X3, X0, X4   ; 需要等待 → 插入1个气泡
```

#### 控制冒险（Control Hazard）

分支指令导致取指方向不确定：

**解决方法**：
1. **分支预测**：预测分支方向，投机取指
2. **预测错误惩罚**：清空流水线，从正确地址重新取指

#### 结构冒险（Structural Hazard）

多个指令同时竞争同一硬件资源：
- 统一缓存同时被IF和MEM访问 → 分离I-cache和D-cache
- 单写端口寄存器文件 → 多写端口或多体寄存器

### 2.3 流水线深度与性能

现代CPU的流水线深度远超过5级：

| 处理器 | 流水线级数 |
|--------|-----------|
| Intel Pentium 4 | 31级 |
| Intel Core i7 | 14\~19级 |
| AMD Zen 4 | 19级 |
| ARM Cortex-X4 | 10级 |
| Apple M1 Firestorm | 9级 |

**深度流水线的权衡**：
- 优点：提高时钟频率，缩短每级逻辑延迟
- 缺点：增加分支预测错误惩罚，增加流水线气泡

## 3. 超标量发射

### 3.1 超标量概念

超标量处理器在每个时钟周期发射**多条指令**到多个执行单元。

**发射宽度**：每个周期最多发射的指令数

| 处理器 | 发射宽度 | 整数ALU | 加载单元 |
|--------|---------|---------|---------|
| ARM Cortex-A77 | 4/周期 | 4 | 2 |
| Intel Core i9-13900K (Raptor Cove) | 6/周期 | 6 | 3 |
| AMD Zen 4 | 8/周期 | 8 | 3 |
| Apple M1 Firestorm | 8/周期 | 6 | 3 |

### 3.2 指令发射策略

#### 按序发射（In-Order Issue）

- 指令按程序顺序进入功能单元
- 实现简单，但遇到长延迟指令时后续指令被阻塞
- 典型应用：低功耗CPU（ARM Cortex-A53）

#### 乱序发射（Out-of-Order Issue）

- 指令不按程序顺序进入功能单元
- 后序指令可以越过等待资源的指令先执行
- 典型应用：高性能CPU（Intel Core, AMD Zen, Apple M系列）

### 3.3 指令发射的限制

**硬件限制**：
- 解码宽度：每个周期最多解码的指令数
- 发射队列大小：等待发射的指令条目数
- 功能单元数量：每种类型的执行单元数
- 寄存器文件端口：同时读写的寄存器数量

**软件限制**：
- 指令级并行度（ILP）：程序中可并行执行的指令比例
- 数据依赖链：连续依赖的指令序列

## 4. 分支预测

分支预测是现代CPU性能的关键，错误预测会导致大量流水线冲刷。在每周期发射6\~8条指令的处理器中，一个误预测损失200+个指令发射机会，因此预测准确率从95%提高到99%意味着性能提升数个百分点——这是微架构设计中投入产出比最高的部分。

### 4.1 分支预测的必要性与工作机制

#### 为什么分支预测如此重要

取指阶段（IF）必须决定"下一条指令从哪里取"。但分支指令要到流水线后端（EX或更晚）才知道真正的方向和目标。如果等待分支结果，前端会停顿10\~19个周期。

```
无分支预测:
  IF ──→ (等待... ......10~19周期... ...) ──→ 确定方向 ──→ 继续取指
              每条分支指令都浪费整个前端深度的周期

有分支预测:
  IF ──→ 预测方向和目标 ──→ 立即从预测地址继续取指 ──→ 后端验证
                                            ↓
                                    预测正确: 零开销
                                    预测错误: 冲刷流水线
```

**性能公式**：平均每条指令因分支损失的时间：

$$
\text{分支开销} = \frac{\text{分支频率} \times \text{误预测率} \times \text{误预测惩罚}}{1}
$$

典型值：分支频率20%，误预测率1%，惩罚17周期 → 每条指令平均损失0.034周期。若无预测（100%误预测率），损失高达3.4周期/指令——CPU慢3倍以上。

#### 预测的两个独立维度

| 维度 | 问题 | 预测器 |
|------|------|--------|
| **方向** | 条件分支跳还是不跳？ | BHT/PHT/TAGE |
| **目标** | 跳转到哪个地址？ | BTB/RAS/ITTAGE |

两个维度独立工作：即使方向预测正确，目标预测错误同样是误预测。

#### 预测器在流水线中的位置

现代CPU采用多级预测，越早的预测越快但越不准确：

```
IF阶段早期 → L0 BTB + 简单方向预测器（0周期延迟，覆盖下一条取指）
     ↓
IF阶段后期 → L1 BTB + 完整方向预测器（1~2周期延迟，可修正早期预测）
     ↓
预解码/解码 → L2 BTB + TAGE类预测器（3+周期，发现更多分支并修正）
     ↓
执行阶段 → 分支单元验证预测，正确则无事发生
     ↓
误预测 → 冲刷流水线，从正确地址重启前端
```

### 4.2 基础动态预测器

#### 2位饱和计数器

最简单的动态预测单元，用一个2位计数器记录单个分支的倾向：

```
        预测不跳转                       预测跳转
          00 ──────────────→ 01 ──────────────→ 10 ──────────────→ 11
        强不跳转           弱不跳转           弱跳转            强跳转
          ↑ ←────────────── ↑ ←────────────── ↑ ←────────────── ↑
              实际不跳转          实际不跳转         实际不跳转

规则:
  实际跳转   → 计数器 +1（饱和在11）
  实际不跳转 → 计数器 -1（饱和在00）
  预测 = 计数器最高位（10和11预测跳转）
```

**为什么用2位而不是1位**：1位计数器在循环分支上，每次循环退出都会预测错一次。2位计数器需要**连续两次**反方向才能翻转预测，循环内的偶发干扰不会翻转倾向。

```
循环执行10次的分支（T=跳转, N=退出）:
  模式: T T T T T T T T T N T T T T T T T T T N ...
  
  1位计数器:  每个N之后第一次T预测错误 → 每轮错1次（90%准确率）
  2位计数器:  N-N才会翻转，单个N不改变强跳转倾向 → 每轮错0~1次（95%+准确率）
```

#### 分支历史表（BHT/PHT）

将2位饱和计数器组织成表，用PC低位索引：

```
分支指令地址: 0x7fff1234
                              ┌──────────────┐
                              │  PHT         │
索引 = PC[11:2] ───────────→ │ [0]  10 (T)  │
                              │ [1]  00 (N)  │
                              │ [2]  11 (T)  │ ← 命中
                              │ [3]  01 (N)  │
                              │ ...          │
                              └──────────────┘
                               读取计数器高位 → 方向预测
```

- PHT大小：典型4K\~16K条目
- **别名冲突**：不同分支映射到同一计数器，互相污染。对策：增大PHT、加标签、或用历史散列

**准确率**：约90\~95%（对行为稳定的分支）

### 4.3 两级自适应预测器

只看分支自身倾向无法捕捉"分支间关联"和"分支自身的历史模式"。两级自适应预测器引入**历史信息**。

#### 核心组件

```
                         ┌──────────────────┐
分支结果 T/N ──移位──→ │ 全局历史寄存器GHR │──索引──→ ┌──────────┐
                         │ (N位，每分支1bit) │          │   PHT    │──→ 预测
                         └──────────────────┘          │ 2位计数器 │
                                                       └──────────┘
```

- **全局历史寄存器（GHR）**：移位寄存器，记录最近N个分支的方向（1bit/分支）
- **模式历史表（PHT）**：由历史索引的2位计数器表

**原理**：同一个分支在不同历史上下文中行为不同。用历史索引，相当于为每个"历史模式"维护独立计数器。

#### 历史模式的威力：示例

```
程序模式: A分支的结果序列为 N T T N T T N T T ...（周期3）

只看自身倾向: 计数器学不到周期模式 → 预测约67%准确

加入全局历史（前2个分支的结果）:
  上下文 NN → 下次N    （计数器学会）
  上下文 NT → 下次T
  上下文 TT → 下次N
  上下文 TN → 下次T
  → 每种上下文对应唯一结果 → 100%准确！
```

#### 变体：如何组合PC和历史

| 变体 | 索引方式 | 特点 |
|------|---------|------|
| GAg | 仅GHR | 全局历史共享一张表，捕捉关联但冲突多 |
| GAp | 仅GHR（多张表） | 减少冲突，面积更大 |
| PAg | PC选表 + GHR索引 | 每个分支有自己的历史表 |
| PAp | PC选历史 + PC选表 | 最细粒度，面积最大 |
| **gshare** | `PC XOR GHR` | 简单高效，最经典的折中 |
| **gselect** | `PC低位拼接GHR` | 类似gshare，拼接代替异或 |

```
gshare索引:
  index = PC[N+1:2] ⊕ GHR[N-1:0]
  
  优点: 同一分支在不同历史下分散到不同条目
        不同分支也均匀分散（XOR散列特性）
  局限: 历史长度不能超过索引宽度
```

**gshare准确率**：95\~98%，是 academia 和早期工业界的主力方案。

### 4.4 混合（锦标赛）预测器

不同预测器各有所长：短历史学得快，长历史捕捉复杂模式但训练慢。混合预测器让多个预测器竞争，用选择器动态挑选当前最准的那个。

#### 经典案例：Alpha 21264（1998）

```
                          ┌─────────────────┐
                          │ 全局预测器       │
                          │ (12位全局历史)   │──→ 预测A
PC ──┬──────────────────→ └─────────────────┘
     │                      ↑比较↑
     ├──────────────────→ ┌─────────────────┐
     │                    │ 局部预测器       │
     │                    │ (每分支10位局史) │──→ 预测B
     │                    └─────────────────┘
     │                           ↑
     └──────────────────→ ┌─────────────────┐
                          │ 选择器 (Chooser) │──→ 最终预测
                          │ 2位计数器/分支   │
                          └─────────────────┘

工作方式:
  选择器比较A和B的最近表现
  如果A最近更准 → 选择A
  如果B最近更准 → 选择B
```

**效果**：比任何单一预测器都好——代码里循环多时局部预测器胜出，分支关联性强时全局预测器胜出，选择器自动切换。

### 4.5 TAGE预测器详解

**TAGE（TAgged GEometric history length）**是当前学术界CBP（Championship Branch Prediction）竞赛冠军，也是现代高性能CPU（Intel/AMD/Apple）方向预测器的原型。

#### 设计动机

- gshare的历史长度固定——短了学不到复杂模式，长了训练极慢且冲突多
- TAGE的核心思想：**多张表，历史长度几何级数递增，让硬件自动找到"够用的最短历史"**

#### 结构

```
                    全局历史 GHR (最长194位)
                    ┌──┬──┬──┬──┬──┬──┬──┬──┬──┬──┐
                    │H1│H2│H3│H4│H5│H6│H7│H8│H9│...│
                    └──┴──┴──┴──┴──┴──┴──┴──┴──┴──┘
                     ↓  ↓  ↓  ↓  ↓  ↓  ↓  ↓  ↓
基础表   ┌────────┐ ┌────────┐ ┌────────┐     ┌────────┐
(无历史) │ PHT    │ │表1     │ │表2     │ ... │表N     │
        │2位计数 │ │Tag+计数│ │Tag+计数│     │Tag+计数│
        └────────┘ └────────┘ └────────┘     └────────┘
           ↑           ↑         ↑              ↑
        PC索引     PC⊕折叠H2  PC⊕折叠H3     PC⊕折叠H194
                  历史长度2   历史长度4      历史长度194

        历史长度: 2, 4, 8, 16, ... 128, 194（几何级数）
```

#### 每张表的结构

| 字段 | 作用 |
|------|------|
| **Tag** | 检查"这个条目确实属于当前分支+历史组合"，避免别名 |
| **2位计数器** | 方向预测 |
| **3位u（useful）计数器** | 该条目是否在被真实使用，用于替换决策 |
| **置信度（ctr高位）** | 预测的"确定程度" |

#### 预测流程

```
① 并行查询所有表（用各自历史长度的折叠散列索引）
② 检查各表Tag是否匹配
③ 取"历史最长的匹配表"的预测 ← 核心规则
④ 若全部未命中 → 用基础表（无历史）的预测

为什么取最长历史:
  长历史表能区分更多上下文 → 匹配说明找到了精确模式
  短历史表只作为"还没学长历史"时的回退
```

#### 训练与分配

```
预测错误时:
① 找到比"当前命中表"历史更长的下一张表 T
② 在T中分配新条目:
   - 若有空闲条目 → 直接分配
   - 无空闲 → 用3位u计数器决定替换（u=0的优先替换；全被占用则全部u减半再重试）
③ 新条目初始化为弱预测，Tag = 当前(PC,历史)的散列

预测正确时:
① 更新命中表的方向计数器
② 更新u计数器（确认条目有效，保护不被替换）
```

#### TAGE为什么强

| 特性 | 收益 |
|------|------|
| 几何级数历史长度 | 每个分支自动匹配"够用的最短历史"——短模式快速训练，长模式有表可查 |
| Tagged表 | 别名污染大幅减少 |
| 最长匹配优先 | 自然偏向更精确的模式 |
| u计数器替换 | 保留真正有用的条目，淘汰噪音 |
| 一次分配一张 | 训练成本可控 |

**准确率**：SPEC CPU上可达99%+，比gshare高出数个百分点——在高发射宽度CPU上就是显著的性能差距。

### 4.6 感知机预测器

用**机器学习**做分支预测：把历史当作特征向量，用一个线性分类器输出预测方向。

#### 数学原理

$$
y = w_0 + \sum_{i=1}^{N} w_i \cdot x_i, \quad x_i \in \{+1, -1\}
$$

- $x_i$：全局历史的第i位（跳转=+1，不跳转=-1）
- $w_i$：第i位历史的权重（学习到的相关性强度）
- $y$：加权和。$y \geq 0$ 预测跳转，$y < 0$ 预测不跳转

#### 训练规则

$$
w_i \leftarrow w_i + \eta \cdot (t - \text{sign}(y)) \cdot x_i
$$

- $t$：实际方向（+1/-1）
- 预测正确且 $|y|$ 足够大（自信）→ 不更新
- 预测错误或不自信 → 按实际方向调整权重

**直观理解**：如果"第5个历史位总是与本分支同向"，那么 $w_5$ 会被训练成大正数；反向相关则变成大负数；不相关则趋近0。

#### 优点与局限

| 优点 | 局限 |
|------|------|
| 理论上能学习线性可分的任意长历史模式 | 只能学**线性**关系，非线性模式（如XOR关联）学不到 |
| 历史长度不受表容量限制（权重共享） | 需要多张感知机表处理多分支（PC选权重表） |
| Jiménez & Lin 2001年提出后曾获CBP冠军 | 硬件乘加开销大，最终被TAGE家族超越 |

### 4.7 分支目标缓冲器（BTB）

方向预测解决"跳不跳"，BTB解决"跳到哪里"。

#### 结构与工作方式

```
IF阶段（在指令解码之前！）:
                                    ┌───────────────────────────┐
  取指地址 ────────────────────→   │ BTB                        │
                                    ├────┬──────┬────────┬──────┤
                                    │Tag │ 目标 │ 类型   │ 元数据│
                                    │... │ addr │ cond/  │ ...  │
                                    │    │      │ ret/   │      │
                                    │    │      │ indir  │      │
                                    └────┴──────┴────────┴──────┘
                                      ↓ 命中
                                    假设是条件分支且预测跳转
                                    → 下一拍从"目标地址"取指
```

**关键点**：BTB在**取指的同时**就给出目标——它甚至不需要知道取出来的指令是什么，只根据取指地址"猜"这里有条分支。这是0周期目标预测的唯一方法。

#### 条目内容

| 字段 | 说明 |
|------|------|
| Tag | 取指地址高位，防别名 |
| 目标地址 | 分支跳转的目的地（全目标，或低位+隐含高位） |
| 分支类型 | 条件分支/直接跳转/间接跳转/返回/调用 |
| 方向预测 | 简单计数器（快速路径）或指向TAGE的指针 |
| 元数据 | way信息、LRU、是否跨缓存行等 |

#### 容量与层次

现代CPU的BTB是分层的：

| 处理器 | L0 BTB | L1 BTB | L2 BTB |
|--------|--------|--------|--------|
| Intel Skylake | ~64条目（μop流） | 1.5K | 2.5K+ |
| AMD Zen 4 | - | 6.5K | 12K+（更大覆盖） |
| Apple Firestorm | 大容量 | 更大 | （未公开，推测巨大） |
| ARM Cortex-X4 | ~64 | 数百 | 数千 |

**层次的意义**：L0小而快（下条指令立即用），L2大而慢（提前填充，覆盖更大的代码足迹）。工作集超出BTB容量时误预测率骤增——这就是大代码库（数据库、浏览器）对小基准测试更难预测的原因之一。

#### x86_64的特殊挑战：预解码

AArch64定长指令，取16字节必含4条指令，哪条是分支一目了然。x86_64变长指令（1\~15字节），**必须先预解码才知道边界和分支**：

```
x86取指流程:
  L1 I-cache 读16字节 ──→ 预解码器扫描指令边界 ──→ 标记分支 ──→ BTB配合
                          （1~2周期）              （预解码位缓存于I-cache）

预解码开销的对策:
  ① I-cache行附带预解码位（每次写行计算一次，命中时直接用）
  ② μop Cache直接存储解码结果+分支信息，绕过整个流程
```

### 4.8 返回地址栈（RAS）

函数返回（RET）是间接分支——目标在运行时由栈决定，BTB只能记住最近一次的返回地址，无法应对多个调用点。

#### 结构

```
        CALL执行时                    RET执行时
     ┌──────────────┐             ┌──────────────┐
     │ 压入返回地址  │             │ 弹出预测目标  │
     └──────┬───────┘             └──────┬───────┘
            ↓                            ↓
  RAS: ┌────┬────┬────┬────┐    ┌────┬────┬────┬────┐
       │addr│addr│addr│....│←── │top │addr│addr│....│
       └────┴────┴────┴────┘    └────┴────┴────┴────┘
       深度16~32条目（匹配典型调用嵌套深度）
```

**为什么RAS有效**：函数调用遵循栈式LIFO模式。RET的目标就是最近一次CALL的下一条指令——RAS用硬件栈精确复刻了这个语义。

#### 推测执行下的RAS难题

推测执行中，CALL/RET是**预测性地**执行（可能随后被冲刷）。RAS的压栈/弹栈操作随之变成推测性的：

```
问题场景:
  推测路径: CALL f（压栈）→ RET（弹出）
  实际: 分支误预测，CALL从未执行
  → RAS被错误地弹了一次！后续所有RET预测全部错位
```

**对策——检查点/快照机制**：
- 每次CALL/RET更新RAS时，将旧栈顶指针存入ROB条目（或影子RAS）
- 误预测冲刷时，用检查点**回滚栈顶指针**，恢复RAS状态
- 部分设计（Intel）在RAS满/空时的处理不精确，是可测的微架构行为（安全研究者曾用它做侧信道指纹识别）

#### RAS容量溢出

调用深度超过RAS容量（16\~32）时，最早的返回地址被挤出，深递归函数的内层RET全部误预测。对策：更大的RAS，或溢出时fallback到BTB。

### 4.9 间接分支预测（ITTAGE）

间接跳转（`JMP reg`、虚函数调用、switch跳转表）的目标**完全由寄存器值决定**，且一个间接分支可能有多个目标。

#### 为什么普通BTB不够

```
虚函数调用: obj->draw()
  同一条 JMP 指令，根据obj的实际类型跳到不同实现
  BTB只能记一个目标 → 多态代码频繁切换时全错
```

#### ITTAGE：TAGE思想用于目标预测

```
结构 = TAGE的镜像，只是条目存"目标地址"而非方向:

                    全局历史
                        ↓
  ┌──────┐  ┌──────┐  ┌──────┐       ┌──────┐
  │基础表 │  │表1   │  │表2   │  ...  │表N   │
  │目标  │  │Tag+  │  │Tag+  │       │Tag+  │
  │      │  │目标  │  │目标  │       │目标  │
  └──────┘  └──────┘  └──────┘       └──────┘
  
  索引不仅用PC+分支历史，还可混入:
  - 全局历史（前序分支的结果）
  - 路径历史（前序分支的目标地址低位）
  - 寄存器值散列（部分实现）

预测: 取历史最长的Tag匹配条目的目标地址
```

**直觉**：虚调用的目标通常由"之前的比较分支结果"决定（类型检查的if-else链）。全局历史恰好编码了这些比较结果 → ITTAGE能从历史推断出目标。

**准确率**：间接分支预测可达95\~98%（BTB baseline约85%）。

### 4.10 推测执行与误预测恢复

预测只是"赌"，硬件必须为"赌错"设计恢复机制。

#### 推测执行的安全设计

```
推测执行的铁律:
  ① 前端按预测地址取指、解码、重命名——一切照常
  ② 乱序引擎照常执行推测指令
  ③ 但推测结果不能"退休"（Commit）——ROB卡在分支处
  ④ 分支执行结果出来:
       预测正确 → 分支退休，后面的推测指令陆续退休（白赚！）
       预测错误 → 冲刷一切推测状态
```

#### 误预测恢复的完整流程

```
分支误预测检测（分支单元执行完）:
① 标记ROB中该分支为"误预测"
② 阻止该分支之后的所有指令退休（ROB截断）

恢复前端:
③ 冲刷取指/预解码/解码/重命名各级的推测指令
④ 将PC设为正确的目标地址（分支单元算出的真值）
⑤ 前端从正确地址重新取指（损失前端深度: 5~10周期）

恢复乱序状态:
⑥ 冲刷发射队列中所有"比分支新"的μop
⑦ 回滚寄存器重命名表（RAT）到分支时刻:
     方案A: 遍历ROB回滚映射（慢）
     方案B: 分支处保存RAT检查点，直接恢复（快，RAM开销）
⑧ 恢复内存序缓冲（MOB）中的推测加载/存储
⑨ 回滚全局历史GHR、RAS栈顶（用检查点）

总代价: 10~20周期（Apple的浅流水线）到 17~20周期（Intel/AMD深流水线）
```

#### 分支重命名与RAT检查点

现代CPU在**重命名阶段就为分支建立检查点**，误预测时O(1)恢复：

```
重命名阶段:
  分支μop经过 → 复制当前RAT快照到检查点阵列
  （每周期多个分支 → 多个检查点槽位）

误预测时:
  加载该分支的检查点 → RAT瞬间回到分支前状态
  vs. 无检查点方案: 沿ROB逐条撤销数百条重命名映射（数十周期）
```

**代价**：检查点阵列消耗大量触发器（每槽保存整个RAT映射），是重命名阶段的面积大户。

### 4.11 分支预测与安全（Spectre）

预测机制"无副作用"的传统假设在2018年被Spectre打破。

#### Spectre v1（边界检查绕过）

```c
if (x < array1_size) {          // ① 训练: 让分支几乎总是跳转
    y = array1[x];              // ② 误训练后传入越界x → 预测"跳转" → 推测执行
    z = array2[y * 256];        // ③ 推测执行触碰越界数据 → 污染缓存
}
// ④ 推测被冲刷，寄存器回滚——但缓存痕迹留下了！
// ⑤ 攻击者计时探测array2哪个缓存行被加载 → 反推y → 反推机密
```

**根本原因**：推测执行虽然不改变架构状态（寄存器/内存），但会改变**微架构状态**（缓存、BTB、RAS）——这些侧信道泄露了本不应存在的信息。

#### Spectre v2（分支目标注入）

攻击者训练**受害进程的BTB**，让间接跳转预测到恶意gadget地址，推测执行泄露机密。缓解：BTB刷新（`IBPB`）、间接分支限制（`IBRS`）、retpoline（用RET代替间接JMP绕过预测器）。

#### 硬件/软件缓解对性能的影响

| 缓解措施 | 机制 | 开销 |
|---------|------|------|
| Retpoline | 间接调用改为RET（RAS不可被外部训练） | 间接调用延迟增大 |
| IBRS/STIBP | 每次上下文切换刷新/限制预测器 | 5\~30%（早期微码） |
| 硬件修复 | 新微架构隔离不同上下文的预测器状态 | 逐步降低到<5% |

### 4.12 现代CPU分支预测器实现对比

| 处理器 | 方向预测器 | 目标预测 | 特点 |
|--------|-----------|---------|------|
| Intel (Sunny Cove系) | 类TAGE多表 + 两个全局历史 | 多级BTB + ITTAGE风格间接预测 | 双流水线预测（快速路+精确路） |
| AMD Zen 4 | TAGE-Like + 感知机辅助 | 大容量L2 BTB（12K+） | "预测管线"：多周期深度预测换取精度 |
| Apple Firestorm | 大规模TAGE类（未公开细节） | 巨大BTB + 快速重定向 | 极浅流水线（9级）依赖超准预测 |
| ARM Cortex-X4 | TAGE原型（ARM参考设计） | 多级BTB | 可配置， licensee可定制 |

**设计趋势**：

```
1. 预测流水线化: 允许预测器本身占多周期（Zen 4约5周期重定向），
   换取更大表容量和更高精度——因为精度收益 > 延迟损失

2. 置信度感知: 预测器输出"自信/不自信"位，
   不自信时前端降低取指激进程度或提前准备恢复

3. 上下文隔离: 不同特权级/进程使用独立预测器上下文（安全需求）

4. 跨分支学习: 不仅预测，还学习"分支相关性图"（如分支A的结果
   依赖于分支B的结果）——BAGE/BT-bifold等前沿研究
```

### 4.13 分支预测性能

| 分支类型 | 预测准确率 | 占比 |
|---------|-----------|------|
| 循环分支 | >99% | 20% |
| if-else 模式 | 95\~99% | 30% |
| 数据相关分支 | 50\~80% | 10% |
| 间接跳转 | 85\~98%（ITTAGE） | 5% |
| 函数返回 | >99%（RAS） | 35% |

**总体预测准确率**：现代CPU达到95\~99.5%以上（SPEC CPU整数）。

**剩余的不可预测部分**：数据相关的分支（如哈希表查找成功与否）本质上由输入数据决定，硬件无法学习——这是分支预测的理论上限，也是编译器层面的**谓词执行（Predication，如AArch64的CSEL/CSINC）、cmov**等技术存在的原因：把分支变成无分支的数据选择。

## 5. 乱序执行

### 5.1 寄存器重命名

**问题**：程序中的寄存器名称在硬件层面可以被复用，但指令间的写后写（WAW）和写后读（WAR）依赖会限制并行度。

**解决**：物理寄存器数量多于架构寄存器数量，通过寄存器重命名消除伪依赖。

```
// 原始代码（WAW 和 WAR 冲突）
ADD  R1, R2, R3   // 写 R1
SUB  R4, R1, R5   // 读 R1（真依赖，不可消除）
MUL  R1, R6, R7   // 写 R1（WAW，与ADD冲突）
ADD  R8, R1, R9   // 读 R1（WAR，与SUB共享R1）

// 重命名后（消除伪依赖）
ADD  P1, P2, P3   // R1 → P1
SUB  P4, P1, P5   // R1 → P1（真依赖保留）
MUL  P6, P7, P8   // R1 → P6（WAW消除）
ADD  P9, P6, P10  // R1 → P6（WAR消除）
```

**物理寄存器文件**：现代CPU通常有200\~400个物理寄存器，而架构寄存器只有16\~31个。

### 5.2 Tomasulo算法

Tomasulo算法是乱序执行的核心，由IBM 360/91（1967）首先使用，至今仍是所有乱序CPU的基础。

**核心组件**：
1. **保留站（Reservation Station, RS）**：等待发射的指令，跟踪操作数是否就绪
2. **公共数据总线（Common Data Bus, CDB）**：结果广播给所有等待的指令
3. **寄存器重命名表（Register Alias Table, RAT）**：架构寄存器到物理寄存器的映射

**指令执行流程**：

```
发射（Issue）→ 读操作数 → 执行（Execute）→ 写结果（Writeback）
    ↓
分配保留站条目、重命名寄存器
```

**发射条件**：
- 保留站有空闲条目
- 寄存器重命名表有空闲物理寄存器
- 功能单元可用

### 5.3 重排序缓冲（ROB）

**ROB的作用**：按程序顺序提交指令结果，实现精确异常。

**ROB条目包含**：
- 指令类型和目的寄存器
- 旧物理寄存器编号（用于恢复）
- 结果值或状态
- 异常信息

**指令提交（Commit）**：
- 当ROB中最老的指令完成且无异常时，提交结果
- 提交后，物理寄存器可以被回收
- 如果发生异常，清空ROB中所有后续指令，恢复到异常点

**精确异常**：即使指令乱序执行，异常发生时处理器状态仍与程序顺序一致。

### 5.4 乱序执行流水线

现代乱序CPU的流水线结构：

```
         取指 → 预解码 → 解码 → 重命名 → 发射队列 → 调度 → 执行 → 写回 → 提交
         (IF)  (PreDec) (Dec)  (Rename) (IssueQ)  (Sch) (EX)  (WB)   (Commit)

前端（Frontend）                   发射队列             执行后端（Backend）
按序取指译码                       乱序等待            乱序执行，按序提交
```

**关键流水线级**：
1. **取指（IF）**：从I-cache取指令，分支预测
2. **预解码（PreDec）**：识别指令边界（x86_64），标记分支
3. **解码（Dec）**：将指令翻译为微操作（μops）
4. **重命名（Rename）**：寄存器重命名，分配资源
5. **发射队列（IssueQ）**：乱序等待操作数就绪
6. **调度（Schedule）**：选择就绪指令发送到执行单元
7. **执行（EX）**：实际计算
8. **写回（WB）**：结果写入物理寄存器，广播到CDB
9. **提交（Commit）**：按序提交，释放资源

### 5.5 微操作缓存（μop Cache）

**问题**：x86_64变长指令解码复杂，功耗高，且每周期解码有限。

**解决**：缓存解码后的微操作，绕过重复解码。

- Intel Core：μop Cache（约1.5K\~2.25K μops）
- AMD Zen：μop Cache（OP Cache，约4K\~6.75K μops）

**效果**：在代码驻留（如循环）时，IF/Dec阶段可以关闭，节省功耗并提高带宽。

## 6. 指令集差异与前端设计

### 6.1 x86_64 解码挑战

x86_64指令编码是CISC风格，指令长度1\~15字节，解码复杂度高：

```
指令前缀（可选，1\~4字节） → 操作码（1\~3字节） → ModR/M → SIB → 偏移量 → 立即数
```

**解码器设计**：预解码器首先扫描指令边界（指令长度），然后将指令分割为多个简单微操作。

**复杂指令拆分**：一条x86指令可能拆分为多个μop：

| x86指令 | 拆分为μops |
|---------|-----------|
| `ADD reg, reg` | 1 μop |
| `ADD [mem], reg` | 2 μops（加载+运算+存储） |
| `REP MOVS` | 多次迭代，每次2 μops |
| `DIV reg` | 多个μops（微码序列） |

### 6.2 AArch64 解码优势

AArch64指令定长4字节，解码相对简单：

- 指令格式规整，操作码位置固定
- 不需要复杂的指令边界检测
- 译码宽度可以更大（8\~10条/周期）

**代价**：代码密度较低（相同功能需要更多指令），但通过压缩指令集（Thumb-2）和优化的编译器缓解。

### 6.3 微码（Microcode）

**复杂指令**（如x86的字符串操作、系统指令）由微码引擎执行：

- 微码是一个内部的简单RISC指令序列
- 存储在ROM中的微码序列
- 遇到复杂指令时，触发微码序列生成多个μop

**微码更新**：现代CPU可以通过微码补丁修复硬件错误（如Spectre/Meltdown漏洞修复）。

## 7. 执行单元

### 7.1 功能单元类型

现代CPU包含多种执行单元，每个单元可以独立执行特定类型的操作：

| 单元类型 | 功能 | 数量（典型） |
|---------|------|-------------|
| 整数ALU | 加减、逻辑、移位 | 4\~6 |
| 整数乘法/除法 | 乘法、除法 | 1\~2 |
| 浮点加法（FP-Add） | 浮点加减 | 1\~2 |
| 浮点乘法（FP-Mul） | 浮点乘除 | 1\~2 |
| SIMD/向量单元 | 向量运算 | 2\~4 |
| 加载单元（Load） | 从D-cache加载 | 2\~3 |
| 存储单元（Store） | 写入D-cache | 1\~2 |
| 分支单元（Branch） | 分支执行与预测更新 | 1\~2 |

### 7.2 执行延迟

不同指令的执行延迟差异很大：

| 操作 | 延迟（周期） | 吞吐量（每周期） |
|-----|------------|----------------|
| 整数加法 | 1 | 4\~6 |
| 整数乘法 | 3\~4 | 1\~2 |
| 整数除法 | 10\~40 | 1/10\~1/40 |
| 浮点加法 | 3\~4 | 1\~2 |
| 浮点乘法 | 4\~5 | 1\~2 |
| 浮点除法 | 10\~20 | 1/10\~1/20 |
| 加载（L1命中） | 4\~5 | 2\~3 |
| 加载（L2命中） | 12\~15 | 1\~2 |
| 加载（L3命中） | 30\~50 | 部分 |
| 加载（内存） | 100\~300+ | 极小 |

### 7.3 向量与SIMD

现代CPU通过SIMD指令实现数据级并行：

| ISA | SIMD扩展 | 寄存器宽度 | 典型指令 |
|-----|---------|-----------|---------|
| x86_64 | SSE/AVX/AVX-512 | 128/256/512位 | ADDPS, VFMADD |
| AArch64 | NEON/SVE/SVE2 | 128\~2048位 | FMLA, LD1 |

**应用**：多媒体处理、科学计算、AI推理（INT8量化）。
